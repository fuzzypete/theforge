# v0.13 Adaptive-Routing Dogfood Readiness Checklist

Companion evidence for issue #1869 (*"v0.13 dogfood readiness checklist"*). This
is the committed, auditable record its acceptance criteria call for: the blocker
disposition, the enable/disable/rollback procedure, the first-dogfood feature
posture, a sample `routing_decision` explanation, and the operator
explainability surfaces.

This document is the **narrow** switch-readiness record for the *first* safe
v0.13 dogfood switch — not a catalogue of every v0.13 feature. Its scope is the
four dogfood-safety properties from the issue: v0.13 must not learn from bad
evidence, must not get stuck in a one-way ratchet, must produce routing
decisions the operator can reconstruct, and must have a clear rollback/disable
path.

Design source of truth: `docs/adr/0006-adaptive-router-trust-boundary.md`
(ADR-0006, Adaptive Router Trust Boundary). Clause references below point into
that ADR.

## 2. Enable, disable, rollback

**AC:** *v0.13 adaptive routing has a documented enable/disable or rollback path
before dogfooding begins.*

Adaptive routing is gated by **two** `forge.yaml` switches under `assignment:`,
and honors the ADR-0006 clause 1 override hierarchy. The operator never has to
edit code or migrate data to turn it off — flipping config back is the whole
rollback.

### The two switches

| Config key | Type | Default | Effect |
|---|---|---|---|
| `assignment.enabled` | bool | `False` | **Master switch.** When `False`, model assignment uses static `forge.yaml` config (`dev_profile`, the reviewer pool from `models.enabled`) — no history, no profiles, no adaptive layer at all. When `True`, adaptive assignment is active. |
| `assignment.adaptive_enabled` | bool | `True` | **History switch,** effective only when `assignment.enabled` is `True`. When `False`, routing is *static band-only*: the complexity score maps to a tier via the score-band table, but no history, profiles, recency, promotions, or domain signals are consulted. When `True`, the full adaptive layer runs. |

Because `assignment.enabled` defaults to `False`, a stock TheForge install does
**not** route adaptively. Turning it on is a deliberate operator opt-in — which is
exactly what makes the switch a decision rather than a surprise (ADR-0006
Consequences → Positive).

### Override hierarchy (ADR-0006 clause 1)

From highest precedence to lowest — higher always wins:

1. **CLI flags** (e.g. an explicit dev/reviewer override on the run command)
2. **Explicit `forge.yaml` configuration** (pinned `dev_profile`, locked roles)
3. **The adaptive layer** (history-driven preference *within* the eligible pool)
4. **Built-in defaults**

The adaptive layer only ever *orders and selects within* the eligible pool set by
layers 1–2. It can never add a candidate static config excludes, nor permanently
remove one static config includes (clause 1: "sort-after, never a filter-out").
This is what bounds the blast radius of turning it on.

### Enable (opt in to adaptive routing)

```yaml
assignment:
  enabled: true
  adaptive_enabled: true   # full adaptive layer (default when enabled)
```

Verify with `forge check-config`: the SETTINGS block prints
`assignment:    enabled  (...)` when the master switch is on.

### Disable — two levels

- **Keep adaptive assignment, drop history (band-only):** set
  `adaptive_enabled: false`. Routing still respects the score-band tier table but
  consults no historical evidence. Use this to isolate "is history the problem?"
  without reverting to fully static config.

  ```yaml
  assignment:
    enabled: true
    adaptive_enabled: false   # static band-only routing
  ```

- **Full disable (static config routing):** set `enabled: false` (or remove the
  `assignment:` block). Assignment falls back to the `dev_profile` and reviewer
  pool declared in `forge.yaml` / `models.enabled`. This is the pre-adaptive
  behavior.

  ```yaml
  assignment:
    enabled: false
  ```

### Rollback (undo a bad switch, mid-dogfood)

1. Set `assignment.enabled: false` in `forge.yaml`. This takes effect on the next
   run — routing immediately reverts to static config. No migration, no data
   deletion, no restart of in-flight state is required.
2. Confirm with `forge check-config` that the SETTINGS block no longer reports
   `assignment: enabled`.
3. **No evidence is lost or must be purged.** Accumulated history stays in the
   audit substrate; it simply stops influencing routing. Recency weighting
   (clause 2.4) means even if you later re-enable, stale evidence decays out of
   relevance on its own timeline rather than permanently biasing the router —
   `forge migrate-profiles` is *not* a forced choice between losing history and
   poisoning routing (ADR-0006 Consequences → Positive, "Migration safety").

Rollback is intentionally cheap because the adaptive layer is *preference*, not
*eligibility*: turning it off returns to the operator-defined static universe
that was always the fallback floor.

## 3. First-dogfood feature posture

**AC:** *Known adaptive features that should remain disabled for first dogfood are
listed with their config/default posture.*

Inventory of every adaptive mechanism the router can run, its config field and
built-in default, whether it is allowed for the *first* dogfood switch, and why.
Defaults are read from `src/theforge/config/types.py`
(`AssignmentConfig` / `RecencyConfig` / `ExplorationConfig`). **No defaults were
changed by this checklist** — the disabled-by-default posture the ADR intends is
already what the code ships.

| Adaptive feature | Config field | Default | First-dogfood posture | Reason |
|---|---|---|---|---|
| Master adaptive assignment | `assignment.enabled` | `False` | **Operator opt-in** | Off by default; the switch itself is the deliberate first-dogfood decision (§2). |
| History-driven preference | `assignment.adaptive_enabled` | `True` | **Allowed** (inert unless master on) | The core v0.13 behavior under test; gated behind the master switch. |
| Recency weighting | `assignment.recency.mode` | `"exponential"` (half-life 50 runs, window 200) | **Allowed** | Passive recovery path (clause 2.4) — prevents stale evidence from poisoning routing; safer *on* than off. |
| Reviewer completion demotion | `reviewer_completion_threshold` = `0.5`, `reviewer_completion_min_runs` = `5` | on | **Allowed** | Sort-after, not filter-out; min-runs floor protects cold-start reviewers (clause 2.2/2.3). |
| Post-plan dev-tier reduction (#1387) | `assignment.plan_tier_reduction` | `True` | **Allowed** | A demotion path — counters promotion creep; the recovery side of clause 5. |
| Escalation memory | `assignment.escalation_memory` | `True` | **Allowed** | Promotion path with recency decay as its passive inverse. |
| Cross-provider preference | `assignment.prefer_cross_provider` | `True` | **Allowed** | Diversity heuristic within the eligible pool; no ratchet. |
| **Exploration / challenger sampling** | `assignment.exploration.per_sprint_cap` = `1` (`explore_every_n` = `5`, `min_sample_size` = `3`) | on (cap 1/sprint) | **Recommend DISABLE for first switch** — set `per_sprint_cap: 0` | Exploration is the one sanctioned *non-deterministic* deviation (clause 8). For the first dogfood the goal is a deterministic, reconstructable baseline and predictable spend; off-policy challenger races add both variance and cost before enough admissible history exists to make them worthwhile. Re-enable once the baseline is trusted. |

To pin the recommended first-switch posture explicitly:

```yaml
assignment:
  enabled: true
  adaptive_enabled: true
  exploration:
    per_sprint_cap: 0    # deterministic first dogfood; re-enable after baseline is trusted
```

Note on exploration even at its default `cap: 1`: a challenger only fires once a
routing key has accumulated `min_sample_size` (3) admissible runs; below that the
slot stays in cold-start static routing. So on a fresh substrate exploration is
largely inert regardless — setting `per_sprint_cap: 0` makes the deterministic
intent explicit rather than relying on the cold-start floor.

Everything else in the table ships enabled and is *safe on* for the first switch
because each is either a recovery path (recency, post-plan reduction), a
sort-after with a cold-start floor (reviewer completion), or a bounded
preference within the eligible pool (cross-provider). None introduces a one-way
ratchet or non-determinism.

## 4. Sample routing_decision explanation

**AC:** *A sample recent run has a usable `routing_decision` explanation for at
least one adaptive routing decision.*

**Status: satisfied by a real router-emitted record.** The evidence is a
committed per-run audit record —
[`docs/assets/sample-routing-decision-run.json`](assets/sample-routing-decision-run.json) —
whose `routing_decision` block was **emitted by the production router**
(`theforge.assignment.assign_models`) with adaptive routing enabled, not
hand-authored. `tests/test_dogfood_readiness_sample.py` re-runs the same router
with the same inputs and asserts the committed record still matches on every
reconstruction-critical field (selected model, the recency-weighted signal, and
the avoided candidate's canonical exclusion reason), so this evidence cannot
silently drift from the code path it documents.

Reproduce the render below verbatim with the shipping CLI:

```
forge explain --file docs/assets/sample-routing-decision-run.json
```

The scenario is a genuine adaptive decision that exercises the recency-weighting
mechanism (ADR-0006 clause 2.4): the `opus` dev profile carries a *poisoned*
lifetime success rate (0.30 over 60 runs) but strong recent outcomes, so the
routing-admissible **weighted** rate (0.9138) diverges sharply from the raw
lifetime average — exactly the "stale evidence poisoning" failure mode the
milestone forecloses. The DEV block shows selected model, an avoided candidate,
the consulted signal with raw + weighted values and sample-floor status, and the
adaptive-mechanism tri-state — everything needed to reconstruct the choice:

```
DEV  (score=9, base tier=strong)
------------------------------------------------------------
    selected: opus [strong]
    rationale: [preflight] complexity score 9 (HIGH) → tier strong (profile success_rate=0.91 @ HIGH)
  candidate pool:
    ✗ sonnet [mid] — excluded — tier does not match role floor
    ✓ opus [strong] — included
        success_rate: raw=0.3000 weighted=0.9138 runs=60 (sample-floor pass)
    ✓ gpt [strong] — included
        success_rate: raw=— weighted=— runs=0 (sample-floor fail)
    ✗ deepseek [strong] — excluded — provider credentials missing
  exploration: winner
  adaptive mechanisms:
    ◐ promotion: checked, did not fire — no_promotion (0/0 matching escalations)
    ○ demotion (dev_tier_demotion): not checked — no_dev_tier_demotion_mechanism_v1
    ○ post-plan checkpoint: not checked — checkpoint_runs_after_plan_review
```

Reading this decision back:

- **Selected model:** `opus` (strong tier). The one-sentence rationale names the
  deciding factor — the recency-weighted profile rate (0.91) at this complexity.
- **Avoided candidate:** `deepseek` (strong tier) — *excluded*, attributed to the
  enumerable reason `auth_missing` ("provider credentials missing"), not a
  free-form string. This is the "why was model X never selected?" answer the
  contract guarantees is greppable (clause 7).
- **Evidence fields:** the consulted `success_rate` signal shows both `raw`
  (0.3000) and `weighted` (0.9138) values, the admissible `runs` count (60), and
  that it cleared the sample floor — the exact fields clause 2 requires to judge
  admissibility, and the raw/weighted drift that makes recency weighting
  *auditable* rather than a black box. `gpt`, with zero recorded runs, visibly
  fails the sample floor and carries no weight (cold-start → static routing).
- **Mechanism transparency:** the tri-state glyphs distinguish *checked-and-fired*
  (`●`) from *checked-did-not-fire* (`◐`) from *not-checked* (`○`), so the
  absence of a mechanism is never confused with a failed condition. The promotion
  check ran and did not fire; the demotion and post-plan mechanisms did not run
  at preflight time (the post-plan checkpoint runs only after plan-review).

The same record's reviewer blocks show the *avoidance* case for a policy
mechanism: in PLAN REVIEW and CODE REVIEW, `opus` is excluded for
`anti_self_review` ("same model as the code under review") — the full "why was
this model avoided?" trail, reconstructable from the record alone.

> **Note on scope.** This is a sample record produced by the real router for
> readiness verification, not the output of a paid live sprint — the first
> *adaptive* dogfood sprint is the switch this checklist gates, and no such
> sprint has run yet. Because the block is emitted by the production
> `assign_models` path (and test-pinned to it), the identical
> `forge explain --run <id>` command reproduces this exact view over a live
> record once the switch is made; the block *is* the contract and the render is
> one presentation of it (ADR-0006 clause 7).

## 5. Operator explainability surfaces

**AC:** *The operator can answer, from status/explain/audit surfaces, why a model
was selected or avoided.*

Three surfaces, with a clear division of labor. The **explain** surface is the
canonical answer to "why this model?"; status and audit are the liveness and
raw-record surfaces that complement it.

| Surface | Command | What it answers | Minimum fields |
|---|---|---|---|
| **Explain** | `forge explain --story <n>` / `--run <id>` / `--file <path>` | *Why was a model selected or avoided?* Renders the `routing_decision` block into a per-role assignment summary. | Selected model + tier per role; excluded candidates with an enumerable exclusion reason; consulted signals with raw + weighted + sample-floor status; adaptive-mechanism tri-state (fired / checked-did-not-fire / not-checked); exploration mode; per-role rationale. |
| **Audit (raw record)** | per-run JSON at `.forge/audits/runs/<run_id>.json`; `forge audit <file>` for the summary log | The *source of truth* the explain view renders. The `routing_decision` block is a top-level field on the per-run record (see the committed sample at `docs/assets/sample-routing-decision-run.json`). | The complete `routing_decision` block verbatim (the contract), plus the run's outcome, cost, and provenance. |
| **Status** | `forge status` | *What is running now / what happened* — liveness and phase progress. | Sprint/run phase and progress. **Does not** render routing rationale — by design; it answers "what," explain answers "why." |

**The operator workflow to answer "why model X?":**

1. `forge status` to find the run/story of interest (liveness).
2. `forge explain --story <n>` (or `--run <id>`) to render the routing decision —
   selected model, avoided candidates with reasons, and the signals/mechanisms
   that drove the choice.
3. If deeper forensics are needed, read the raw `routing_decision` block in
   `.forge/audits/runs/<run_id>.json` directly, or point `forge explain --file`
   at it. The render is a convenience; the recorded block is the contract, so the
   raw record can always reconstruct the decision even without the CLI.

`forge explain` is strictly read-only: it invokes no agents, re-reads no
profiles, and never mutates the substrate (it opens the audit index read-only).
Pre-#1391 records that predate the `routing_decision` contract are reported
explicitly ("no routing_decision block recorded for this run") rather than shown
as a misleading empty summary — so the operator can distinguish "no rationale
recorded" from "rationale is empty."

### Known gap (must-track, not switch-blocking)

- **Status does not surface routing rationale.** By design, `forge status` reports
  liveness only; "why a model was selected" is answered by `forge explain`, which
  reads from the same audit substrate. This satisfies AC #5 (the operator *can*
  answer the question from the explain/audit surfaces end-to-end) but means the
  answer is one command away from `status`, not inline in it. A future ergonomic
  improvement could surface a one-line assignment summary in `status`; it is not
  required for the first dogfood switch because the reconstruction path is
  complete via explain + the raw record.

## Verdict

All five acceptance criteria are **GO**. The two named blockers are closed, the
enable/disable/rollback path is a two-switch config flip with no data migration,
the first-dogfood feature posture is inventoried (with exploration recommended
off for the first switch), a usable `routing_decision` explanation is captured,
and the operator can reconstruct any selection/avoidance decision through
`forge explain` over the audit substrate. The one tracked gap (status shows
liveness, not rationale) is an ergonomic follow-up, not a switch blocker.
