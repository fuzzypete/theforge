# Discovery: Story-First Workflow and Terminology Alignment

Captured 2026-03-17 from ideation session on TheForge terminology, story
format, pipeline flexibility, and decomposition.

---

## Context

TheForge's terminology and artifact format drifted during rapid development.
Specs were written by LLMs during interactive sessions and accumulated
implementation detail that belongs in the PLAN phase, not the story. The
pipeline is all-or-nothing (no partial runs). Decomposition exists only as
a manual upstream step. This discovery doc captures the agreed mental model
and the concrete changes needed.

---

## 1. Terminology Alignment

TheForge's concepts map to familiar SDLC terms. The following terminology
is agreed and should be used consistently in docs, code comments, CLI help
text, and agent prompts going forward.

| Term | Definition | Artifact | CLI Surface |
|------|-----------|----------|-------------|
| **Brief** | Fuzzy problem statement, input to ideation | `briefs/*.md` or inline text | `forge ideate <brief>` |
| **Story** | Atomic executable work unit. Describes WHAT and WHY with behavioral acceptance criteria. No implementation detail. | `specs/*.md` (rename to `stories/` later) | `forge run <story>` |
| **Plan** | Implementation HOW. Generated by PLAN phase from story + codebase. Contains function signatures, data structures, test scenarios, edge cases. | `forge_plan.md` in worktree | `forge run --until plan` |
| **Epic** | Thematic grouping of related stories with a shared vision | `specs/epics/*.md` | Not yet CLI-surfaced |
| **Sprint** | Dependency-aware execution plan with batched stories | `sprints/*.yaml` | `forge sprint <manifest>` |
| **Batch** | Parallel execution layer within a sprint. Stories in the same batch have disjoint `file_scope` and can run concurrently. | Computed by dependency analysis | Internal to sprint runner |
| **Track** | Multi-sprint workstream produced by `forge plan` | `tracks/*.yaml` (future) | `forge plan` (future) |
| **Task** | Runtime execution instance of a story | `TaskSpec` in code | Internal only |

### Key distinctions

- **Story vs Plan:** A story says "Given 3 specs with disjoint file_scope,
  they land in 1 batch." A plan says "Create `ExecutionPlan` dataclass with
  `batches: list[list[SpecNode]]`, implement `build_dependency_graph()` using
  greedy graph coloring." The story is the contract. The plan is the
  implementation strategy.

- **Sprint is not a serial queue.** Today `forge sprint` runs stories
  sequentially. The target architecture (Phases 9+10) makes sprint a
  dependency-aware scheduler that groups non-conflicting stories into
  parallel batches. The term "sprint" stays; its implementation evolves.

- **Spec vs Story in code.** `TaskSpec` in `task.py` stays as-is for now.
  The rename from spec→story is a separate mechanical refactor that should
  run last in any sprint that includes it (it touches everything, changes
  nothing behavioral). Don't rename yet — just use "story" in conversation
  and new documentation.

## 2. Story Format: Lean, Behavioral, No HOW

### The problem with current specs

Every spec in the repo was generated by an LLM during interactive sessions.
They contain exact dataclass definitions, function signatures, code snippets,
file-level implementation steps. Example from `dependency-analysis.md`:

```python
# This is in the SPEC — it shouldn't be
@dataclass(frozen=True)
class SpecNode:
    spec_path: str
    slug: str
    file_scope: frozenset[str]
    unrestricted: bool
```

This pre-solves the implementation before the PLAN agent reads the codebase.
It bakes in stale assumptions, robs PLAN of its job, inflates prompt size,
and makes stories brittle when the codebase changes.

### The correct format

A story contains:

1. **Problem** — what is broken or missing, and why it matters
2. **Requirements** — numbered list of WHAT the solution must do (behavioral,
   not structural)
3. **Acceptance criteria** — observable outcomes a human or test can verify
   from outside. No internal structure, no function names, no data shapes.
4. **Out of scope** — what this story does NOT address
5. **Context** (optional) — describes what IS today, to orient the plan agent.
   Describes current state, not future implementation.

A story does NOT contain:

- Function signatures or method names
- Dataclass/class definitions
- Code snippets or pseudocode
- File-internal implementation steps
- Specific variable or parameter names
- "Design" sections with architectural diagrams of the solution

### Where the HOW lives

| Phase | Produces | Contains |
|-------|----------|----------|
| `forge ideate` | Story | WHAT + WHY + acceptance criteria |
| PLAN phase | `forge_plan.md` | HOW — exact functions, signatures, edge cases, test scenarios |
| DEV phase | Code | Implementation following the plan |
| REVIEW phase | Verdict + findings | Assessment of code against story criteria |

### Existing specs are grandfathered

Do NOT rewrite specs in `specs/`. They work. The lean format applies to
new stories produced by `forge ideate` going forward. The change is in the
ideate synthesis prompt, not in existing artifacts.

## 3. Pipeline Flexibility: Start and Stop Anywhere

### Current state

The pipeline is all-or-nothing:
```
INIT → WORKSPACE → PREFLIGHT → PLAN → DEV → VALIDATE → REVIEW → DONE
```

`forge run` always runs the entire sequence. `forge review` starts at REVIEW.
No other partial runs exist.

### Target state

`forge run <story> --until <phase>` stops after the named phase:

- `--until preflight` — check if story is already done or blocked. Costs
  almost nothing. Useful for validating a sprint manifest before execution.
- `--until plan` — produce `forge_plan.md` and stop. Human reviews the plan
  before committing dev budget. **This is the most important new workflow.**
- `--until dev` — run through VALIDATE and stop. Human inspects code before
  burning review budget.
- (no flag) — full pipeline as today.

`forge sprint <manifest> --until plan` applies to every story — batch-plan
an entire sprint without executing it.

### Why this matters

The iterative workflow becomes:
1. `forge ideate <brief>` → story (behavioral, lean)
2. `forge run <story> --until plan` → review the plan
3. If plan looks wrong → adjust story, re-plan
4. If plan looks right → `forge run <story>` → full pipeline

This catches bad stories and bad plans before any dev budget is spent.

## 4. Decomposition: What Exists, What's Missing

### What exists

1. **Preflight complexity classification** — detects small/medium/large.
   Controls whether PLAN runs and whether dev model gets upgraded. Never
   triggers decomposition.

2. **PLAN phase** — reads codebase + story, produces `forge_plan.md`.
   Currently always produces a single plan. Cannot signal "this is too big."

3. **`forge ideate` as DECOMPOSE** — Phase 11 in vision. Manual: human
   writes a brief asking "what sub-problems does this contain?", runs
   `forge ideate`, reviews output, creates sprint manifest. No automatic
   trigger.

### Gaps

1. **No automatic "too big" detection that acts.** Preflight says "large"
   but the coordinator just upgrades the model. The coordinator refactor
   failure is the proof: sonnet timed out 3x, burned $6+, never decomposed.

2. **No grooming step.** No lightweight checkpoint that says "stop, break
   this up" before dev budget is spent.

3. **PLAN can detect but can't act.** PLAN reads the full codebase and is
   best positioned to say "this is really 4 sequential changes." But it has
   no way to signal decomposition, and the coordinator can't receive it.

4. **No sub-story execution model.** `forge sprint` runs independent stories
   in separate worktrees. Decomposed sub-stories need shared worktree and
   sequential execution within a single logical unit.

### Strategy

Upstream decomposition (making it easy to decompose before running) is
higher leverage than runtime decomposition (PLAN discovers it's too big
mid-run). The combination of lean stories + `--until plan` + ideate makes
upstream decomposition nearly frictionless. Runtime decomposition (PLAN
signaling DECOMPOSE_NEEDED) is Phase 11 territory.

## 5. Sprint Plan

### Sprint 1: Observability (run first)

**Purpose:** Generate data to understand why stories fail review.

| Story | What it does |
|-------|-------------|
| `agent-trace-artifacts` | Write full agent output, prompts, gate output, and reviewer text to trace files in the worktree after every invocation. Post-mortem debugging without re-running. |

After this sprint, run existing backlog stories. Failures leave traces.
Analyze traces to determine root causes before changing story format or
pipeline.

### Sprint 2: Story-first workflow (run after analyzing Sprint 1 data)

**Purpose:** Fix the input quality and pipeline flexibility problems.

| Story | What it does |
|-------|-------------|
| `lean-story-output` | Change `forge ideate` synthesis prompts to produce behavioral stories with no implementation detail |
| `pipeline-entry-points` | Add `--until <phase>` flag to `forge run` and `forge sprint` |
| `vision-pipeline-flexibility` | Update vision doc with new terminology, workflow, and story format contract |

### Sprint 3: HITL optimization (future, after Sprint 2)

**Purpose:** Make human decision points faster and better-informed.

| Story | What it does |
|-------|-------------|
| `human-review-brief` | AI-generated decision context in ntfy notifications |
| `decision-surface` | Generalized decision gates with configurable mode (blocking/advisory/auto) |
| AI-assisted decision options | Context-aware, Opus-generated options at every decision gate (needs story) |

### Big rename (run manually via Claude Code, after all sprints)

Rename campaign→sprint and spec→story across the codebase. Mechanical
refactor, no behavioral changes. Touches everything, conflicts with
everything — always runs alone and last.

## 6. Parallelism Architecture (Confirmed)

Single forge with internal parallelism, not multiple forge instances.

The path (Phases 9→10):
1. `build_dependency_graph()` produces batches via greedy graph coloring on
   `file_scope` overlap + explicit `depends_on`
2. Sprint runner executes batches sequentially, stories within a batch
   concurrently in separate worktrees
3. Batch N merges all branches before batch N+1 starts
4. `max_parallel` config caps concurrency (API rate limits, machine resources)

Failure propagation in parallel sprints: if story A (batch 1) fails, story C
(batch 2, depends on A) is skipped. Story D (batch 2, depends on B only)
still runs. Story E (batch 2, no dependencies) still runs. This is DAG-aware
failure propagation, not halt-on-failure.

Multiple forges are the manual workaround until this is built. They work
(isolated worktrees) but lose budget coordination, merge ordering, and
unified audit.
